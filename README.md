# ferry

Разработка на нескольких машинах локальной сети: на этом компьютере (хаб) пишешь код, а собираешь, запускаешь и смотришь на экран — на любом узле, в том числе на настоящем рабочем столе Windows. Рассчитан и на человека, и на Claude: всё — обычные команды с выводом и кодом выхода.

```sh
ferry ls                                     # узлы: на связи ли, отвечает ли рабочий стол
ferry doctor win-10                          # готов ли узел собирать этот проект
ferry run win-10 -- cargo test               # sync + команда в том же подкаталоге проекта на узле
ferry run win-10 --desk -- bunx playwright test --project=live --reporter=line
ferry get win-10 playwright-report           # отчёт, логи, собранный MSI — сюда
ferry start win-10 app -- <команда>          # фоновая задача на рабочем столе: приложение, dev-сервер
ferry log win-10 app -f                      # её лог; выйдет с кодом задачи
ferry tunnel win-10 9322                     # 127.0.0.1:9322 здесь → CDP приложения на узле
ferry windows win-10                         # окна узла: процесс, место, размер, у кого фокус
ferry click win-10 458 390                   # настоящий клик ОС в точку снимка; type, key — ввод
ferry rec win-10 6                           # запись экрана кадрами + лист-обзор
ferry shot win-10                            # снимок экрана → ~/.ferry/shots/win-10.png
ferry pull win-10                            # правки, сделанные на узле, — сюда
ferry stop win-10                            # снять всё, что запущено через --desk
```

`ferry` без аргументов — полный список команд.

## Как устроено

- **Узлы** — Host-блоки в `~/.ferry/ssh_config`. `ferry add` подключает его первой строкой `~/.ssh/config` (`Include`), поэтому `ssh win-10`, `scp` и `git push win-10:…` работают и напрямую. ControlMaster держит одно соединение на узел — остальные команды идут без handshake.
- **Проект** `…/<имя>` хаба живёт на узле в `~/ferry/<имя>`. `sync` (и `run` перед командой) кладёт туда снимок рабочего дерева — с незакоммиченным и новыми файлами. Снимок собирается во временном индексе и коммитится вне веток: ветка и индекс здесь не меняются, а тот же снимок даёт тот же хеш, так что повторный sync почти бесплатный. Файлы из `.gitignore` (`target/`, `node_modules/`) не ездят — кроме перечисленных в `files` настроек проекта (см. ниже).
- **Правки на узле** не теряются: если перед sync на узле есть изменения, которых нет здесь, они сохраняются патчем в `~/.ferry/saved/`. `ferry pull` применяет их к рабочему дереву здесь.
- **Рабочий стол.** По SSH команды на Windows попадают в Session 0, где нет рабочего стола: окна не видны, фокуса нет. Демон `ferry daemon` запускает планировщик при входе пользователя, то есть в его сессии; `--desk` передаёт команду ему через 127.0.0.1 и возвращает вывод и код выхода. Окружение (PATH) демон снимает при старте: поставил инструмент — `ferry restart <узел>`, `doctor` подскажет.

## Фоновые задачи и туннели

`ferry run` ждёт конца команды. Для того, что должно жить дальше — запущенное приложение, dev-сервер, долгая сборка, — фоновая задача:

```sh
ferry start win-10 app -- ./src-tauri/target/debug/logarithmica.exe --remote-debugging-port=9322
ferry jobs win-10                 # работает / завершилась, код N / остановлена
ferry log win-10 app -f           # следить за логом; выйдет с кодом задачи — так можно ждать сборку
ferry start win-10 app -- …       # то же имя ещё раз — перезапуск
ferry kill win-10 app
```

Задача идёт на рабочем столе узла под своим процессом-надсмотрщиком: переживает обрыв ssh и перезапуск демона (`ferry update`), лог и код выхода лежат в `~/.ferry/jobs/<имя>/` на узле. `ferry stop <узел>` снимает и задачи.

Туннель делает порт узла локальным — тем же номером, потому что CDP отдаёт ws-адрес со своим портом:

```sh
ferry tunnel win-10 9322           # 127.0.0.1:9322 здесь → 9322 на узле
ferry tunnel                       # открытые туннели
ferry tunnel win-10 9322 --close
```

Так Playwright и MCP `cef` работают с приложением на узле как с локальным:

```sh
claude mcp add cef-win-10 -- npx -y @playwright/mcp@0.0.83 --cdp-endpoint http://127.0.0.1:9322
```

Playwright из Bun через CDP не подключается (WebSocket так и не открывается) — запускай его на Node.

## Экран узла: окна, ввод, запись

Ввод через CDP идёт в рендерер в обход ОС — нативные баги фокуса так не воспроизвести. Эти команды работают как человек за клавиатурой: `SendInput` и окна ОС (пока только Windows-узлы). Координаты — пиксели снимка `ferry shot`, поэтому цикл «снимок → нашёл кнопку → клик → снимок» работает напрямую.

```sh
ferry windows win-10                     # окна сверху вниз по z-порядку; * — у кого фокус
ferry click win-10 458 390 [right|double]
ferry move win-10 458 390                # навести (hover)
ferry scroll win-10 -3                   # колесо: больше нуля — вверх
ferry type win-10 'Привет, мир'          # юникодом: раскладка не важна; \n и \t — клавишами
ferry key win-10 ctrl+a delete alt+f4    # комбинации по порядку
ferry rec win-10 6 [4]                   # 6 с по 4 кадра → ~/.ferry/recs/<узел>-<время>/
```

`rec` снимает кадры с курсором и печатает путь к `sheet.png` — до 12 равномерно выбранных кадров с отметкой времени на одном листе: по нему видно, что происходило, без просмотра видео. Есть `ffmpeg` на хабе — рядом появится и `video.mp4`.

Чего ввод не может: окна, запущенные от администратора (Windows не пускает ввод из обычного процесса в повышенный), заблокированный экран и окно UAC.

## Настройки проекта

Хранятся на хабе, в репозиторий не попадают: `~/.ferry/projects/<проект>.toml` (`<проект>` — имя каталога репозитория).

```toml
tools = ["cmake", "ninja"]   # doctor проверит их на узлах
files = [".env"]             # sync возит их на узел мимо git
```

Остальное `doctor` выводит из самого репозитория: Rust нужного канала из `rust-toolchain.toml` (и MSVC на Windows), менеджер JS-пакетов по `packageManager` или lock-файлу, доступ к git-хостам из `git@…` в манифестах и lock-файлах.

## Приватные git-зависимости: релей через хаб

Ключ от GitLab/GitHub есть только на хабе, а `cargo`, `bun`, `npm`, `go` и сам `git` на узле всё равно достают приватные репозитории по SSH:

```sh
ferry trust git.logarithmica.ru     # один раз на хабе; ferry trust — список
```

Команды `ferry run` (и `--desk`) получают на узле `GIT_SSH_COMMAND='ferry ssh'`. Для доверенного хоста `ferry ssh` в сеть не ходит: через обратный проброс (`RemoteForward` из Host-блока узла → `~/.ferry/relay.sock` хаба) он просит релей хаба выполнить ту же команду своим ssh и гоняет потоки. Релей поднимается сам при первой команде и выходит после 30 минут простоя.

- **Только чтение**: `git-upload-pack` и `git-upload-archive`. Push с узла релей отклоняет — скомпрометированный узел не запушит от твоего имени.
- **Только доверенные хосты** из `~/.ferry/trust`, аргументы проверяются так, чтобы ни одно поле не стало опцией ssh хаба; доступ к релею — по токену.
- Недоверенные хосты и недоступный релей — обычный ssh узла.
- cargo по умолчанию ходит в git мимо `GIT_SSH_COMMAND`, поэтому ferry ставит ему `CARGO_NET_GIT_FETCH_WITH_CLI=true`.
- Работает, пока хаб на связи; узлы, добавленные до релея, перезапиши: `ferry add <узел> <user@адрес>`.

## Узел на Windows

Нужны Windows 10 1809+ и [Git for Windows](https://git-scm.com/download/win).

На хабе (macOS), один раз:

```sh
brew install mingw-w64
ssh-keygen -t ed25519 -f ~/.ssh/ferry -N ''
cargo install --path .                                    # ferry на хабе
cargo build --release --target x86_64-pc-windows-gnu      # ferry.exe для узла
mkdir -p dist && cp target/x86_64-pc-windows-gnu/release/ferry.exe install.ps1 ~/.ssh/ferry.pub dist/
python3 -m http.server 8000 -d dist                       # раздать установщик на время установки
```

На узле, в PowerShell от администратора, под тем пользователем, на чьём рабочем столе будут идти команды:

```powershell
iwr http://<хаб>:8000/install.ps1 -OutFile $env:TEMP\ferry.ps1 -UseBasicParsing
powershell -ExecutionPolicy Bypass -File $env:TEMP\ferry.ps1 -From http://<хаб>:8000
```

Снова на хабе:

```sh
ferry add win-10 <user>@<адрес>       # user и адреса печатает установщик в конце
ferry doctor win-10                   # чего узлу не хватает для этого проекта
```

Дальше ferry на узле обновляется с хаба: `ferry update win-10 target/x86_64-pc-windows-gnu/release/ferry.exe`.

## Узел сменил адрес

Узел узнаётся по ключу хоста, а не по IP: в его Host-блоке стоит `HostKeyAlias <узел>`, и ssh помнит ключ под именем узла. Если узел не отвечает, `ferry ls` ищет его сам (явно — `ferry find <узел>`):

1. среди устройств tailnet, если на хабе включён Tailscale, — там адрес устройства не зависит от сети, в которой оно сейчас;
2. в локальных сетях хаба (/24 вокруг адреса каждого интерфейса с широковещательным адресом): у кого открыт 22-й порт. VPN и другие туннели не сканируются — это чужие сети, а VPN вдобавок может «открывать» любой адрес.

Узлом признаётся только машина с тем же ключом хоста — чужой sshd за узел себя не выдаст. Найденный адрес записывается в `HostName`. Узел в другой подсети без Tailscale хаб не найдёт — тогда `ferry add <узел> <user@адрес>`.

## Обрыв соединения

Когда `ferry run` прерывают (Ctrl-C, kill, таймаут), ssh закрывает канал, клиент `ferry desk` на узле падает на первой же записи вывода, и демон убивает дерево команды — за секунды. Если умерло само соединение (хаб уснул), то же делает sshd узла по `ClientAliveInterval` (ставит установщик), примерно за 30 с.

Совсем молчаливую команду (`sleep 1000` без вывода) так не снять: Win32-OpenSSH не убивает дочерние процессы закрытой сессии, а клиент без записи обрыва не замечает. Для неё — `ferry stop <узел>`. Тесты, сборки и приложение пишут вывод, их это не касается.
